Next step 1 · the object

Default-deny, then allow one path

1 — shut the namespace 
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
spec:
  podSelector: {}        # every Pod here
  policyTypes: [Ingress]  # …accepts nothing

An empty podSelector means all Pods in the namespace. No ingress: rules means no traffic allowed in.

2 — open exactly one door 
kind: NetworkPolicy
metadata:
  name: frontend-to-backend
spec:
  podSelector:
    matchLabels: {app: backend}
  ingress:
  - from:
    - podSelector:
        matchLabels: {app: frontend}

Labels again — the same glue as Services. Policies are additive: they only ever allow.

A NetworkPolicy is an object, not an enforcer. Your CNI plugin does the enforcing — and if it doesn't implement NetworkPolicy, the API server still accepts your YAML and nothing changes. No error, no warning, no protection. Check your CNI before you trust a policy.
Network Policies
This is the slide that saves them a bad afternoon. The failure mode is silent: `kubectl apply` succeeds, `kubectl get netpol` lists the policy, and traffic flows exactly as before because the CNI ignores it. Say plainly that our kind cluster is one of the environments where this can happen — which is why there is no NetworkPolicy lab today, and why the first thing to do on a real cluster is verify enforcement with a deliberate curl that *should* fail. Two ideas to land: default-deny first then allow (allow-listing, not block-listing), and policies are additive — there is no "deny" rule, so you cannot punch a hole by accident, only forget to open one. Namespace-scoped, like almost everything else (Session 2).
